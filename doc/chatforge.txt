INTRODUCTION                                                *chatforge*

ChatForge keeps an Ollama conversation for each source buffer. Edit requests
stream into the live Neovim buffer as marked proposals. Accept writes a fresh
proposal to disk. Reject restores its saved original lines in memory.

Version 0.2.1 supports one Ollama backend. It handles one active request and
one staged edit workflow at a time. Chat and model state last only for the
current Neovim process.

Context is explicit. Use |chatforge-context| references when a request needs a
file or directory listing. ChatForge does not scan the whole project for every
message.

=============================================================================
REQUIREMENTS AND SETUP                                 *chatforge-setup*

Requirements:

- Neovim 0.10 or newer
- curl in $PATH
- Ollama
- An installed Ollama model

lazy.nvim example: >lua

  {
    "RichardOyelowo/chatforge.nvim",
    version = "v0.2.1",
    cmd = {
      "Chat", "ChatSend", "ChatEdit", "ChatModel", "ChatReset",
      "ChatApply", "ChatAccept", "ChatDiff", "ChatReviewDiff",
      "ChatPreview", "ChatReject", "ChatNextChange", "ChatPrevChange",
      "ChatBackend",
    },
    opts = {
      default_model = "llama3",
      ollama_url = "http://localhost:11434",
    },
  }
<
Start Ollama and install the configured model: >sh

  ollama serve
  ollama pull llama3
<
The commands normally run in separate terminals because `ollama serve` keeps
running. Finish with: >vim

  :checkhealth chatforge
<
render-markdown.nvim and dressing.nvim are optional. See
|chatforge-optional-ui|.

=============================================================================
QUICK START                                        *chatforge-quick-start*

Open a source file and run: >vim

  :Chat
<
Type in the bottom message pane. Press ENTER to send. CTRL-J inserts a newline.

Ask a read-only question: >vim

  :ChatSend review @file for error-handling gaps
<
Request an edit: >vim

  :ChatSend fix the error handling in this file
<
Force a live staged edit regardless of wording: >vim

  :ChatEdit add input validation to this file
<
The first fenced code block starts staging highlighted code in the source
buffer while Ollama responds. Review the marked lines: >vim

  :ChatDiff
  :ChatAccept
<
Use |:ChatReject| instead if the proposal is wrong.

=============================================================================
CHAT WORKFLOW                                        *chatforge-workflow*

|:Chat| opens a 65-column vertical split on the right. The chat is above an
eight-line message pane. Both temporary buffers have `filetype=markdown` and
`buftype=nofile`.

The source buffer that opens ChatForge owns the conversation and model choice.
Open ChatForge from another source buffer to switch sessions.

Messages can be sent in four ways:

1. Run `:ChatSend some text`. Edit-shaped text stages live in the source
   buffer.
2. Run |:ChatEdit| with text to force a live staged source-buffer edit.
3. Run |:ChatSend| without text to focus the message pane. Run it again while
   that pane has focus to send its contents.
4. Select source lines and run `:'<,'>ChatSend`. ChatForge requests replacement
   code and stages it back into that exact range.

Message-pane mappings:

  ENTER     Send. When completion is visible, accept its item first.
  CTRL-J    Insert a newline.

Completion uses buffer-local menu settings. ChatForge does not change the
user's global completion UI.

Normal-mode editing keys in the read-only chat pane redirect to the input.
ChatForge defines no global mappings.

Edit-shaped requests stage code. ChatForge treats prompts that ask to add,
change, update, remove, rewrite, generate, implement, create, improve, or make
code as live edit requests. Plain review and explanation prompts keep fenced
blocks as examples in the chat pane. Accept or reject an existing staged
proposal before sending another message.

=============================================================================
CONTEXT REFERENCES                                     *chatforge-context*

References are case-insensitive. Tokens inside injected source are not parsed
again. This prevents source text from pulling in an unexpected second file.

BARE FILE                                                    *chatforge-@file*

`@file` injects the current live Neovim buffer. Unsaved edits are included.
Nearby prose is not consumed as a path: >vim

  :ChatSend can you review @file fully?
<
`fully?` remains part of the question.

NAMED FILE                                              *chatforge-@{file}*

Use braces for a named file: >vim

  :ChatSend compare @{file lua/old.lua} with @{file lua/new.lua}
  :ChatSend review @{file docs/design notes.md}
<
Named files are read from disk. Relative paths use |:pwd|. Absolute paths,
`~`, and environment variables use `vim.fn.expand()`.

ChatForge also accepts `{afile path}` as a compatibility shorthand for named
file context.

`@{file .}`, `@{file /}`, and an empty file reference mean the current live
buffer. `/` does not mean the filesystem root in this special form.

An unreadable file adds an HTML context error to the model prompt. The request
still runs.

BARE DIRECTORY                                                *chatforge-@dir*

`@dir` injects a sorted, one-level listing of |:pwd|: >vim

  :ChatSend use @dir to explain the project layout
<
Entries are marked `d` for directory or `f` for every other entry type.

NAMED DIRECTORY                                          *chatforge-@{dir}*

Use braces for a named directory: >vim

  :ChatSend inspect @{dir lua/chatforge}
  :ChatSend inspect @{dir source files}
<
Named directory paths stay under |:pwd|. A leading slash is stripped, so
`@{dir /lua}` means `<cwd>/lua`. Absolute directory paths, `~`, and environment
variable expansion are not supported in version 0.2.1.

Directory listings are not recursive. One read returns at most 64 entries.

COMPLETION                                          *chatforge-context-complete*

Typing an `@` reference in the message pane opens completion. ChatForge scans
|:pwd| recursively and offers at most 80 items. Bare `@file` and `@dir` come
first. Directories come before files. Paths under `.git` are skipped.

The list is cached for the current working directory. New paths may not appear
until the working directory changes or Neovim restarts. Manual references still
work.

RELATED FILE CONTEXT                              *chatforge-related-context*

When a message shares file context with `@file`, `@{file path}`, or
`{afile path}`, ChatForge remembers the most recent files in the current Neovim
session. Later prompts that clearly ask about file relationships, such as
whether CSS matches HTML, include those recent files as related context.
|:ChatReset| clears this remembered context.

=============================================================================
INTENT AND AUTOMATIC CONTEXT                           *chatforge-intent*

ChatForge classifies the start of a message. Matching is case-insensitive.

  Wording                   Behavior
  ---------------------------------------------------------------------------
  explain                   Add current-buffer context. Do not stage.
  review, how, what, why    Chat/review mode. Do not stage unless :ChatEdit
                            is used.
  fix                       Add current-buffer context. Stage an edit.
  refactor                  Add current-buffer context. Stage an edit.
  add, change, update,
  remove, rewrite,
  generate, implement,
  create, improve, make     Add current-buffer context. Stage an edit.
  edit file <path>          Add current source context. Stage into <path>.
  create file <path>        Stage into <path>. Add no automatic context.
  delete file <path>        Classify only. Do not delete or stage.
  :ChatEdit <prompt>        Force a live staged edit.
  anything else             Normal chat, unless sent from a visual selection.

Automatic current-buffer context has a 160-line cap. Larger buffers send a
160-line window around the visible cursor. Bare `@file` sends the full live
buffer and bypasses this cap.

An `edit file` or `create file` target ends at whitespace. Target paths cannot
contain spaces. `@{file path}` adds context only. It does not set a staging
target.

=============================================================================
STAGED EDITS                                       *chatforge-staged-edits*

Staging changes a Neovim buffer in memory. It does not write to disk.

Edit-shaped prompts, |:ChatEdit|, `create file`, and visual-selection requests
use streamed Ollama responses. When the first fenced block begins, ChatForge
stages highlighted code in the target buffer. It does not add text markers into
the source buffer.

Targets:

- Edit-shaped prompts without a selected range insert the proposal at the
  source cursor. They do not clear the file.
- A visual selection replaces only its original line range.
- `create file <path>` opens or creates that path in the source window, then
  stages the generated block there.

The buffer becomes modified during staging. Autosave, |:write|, or another
plugin can write the proposal before acceptance. ChatForge does not block those
writes.

ACCEPT

|:ChatAccept| and |:ChatApply| compare the current buffer `changedtick` with the
value recorded after staging. A fresh proposal is written with `:write`. Its
marks and staged metadata are then cleared. Unnamed and special buffers are not
written, but their staged state is cleared.

REJECT

|:ChatReject| performs the same `changedtick` check. A fresh proposal is
replaced with the saved original lines. The restoration is not written to disk.

STALE PROTECTION                                    *chatforge-stale*

Any buffer change after staging makes the proposal stale. Manual edits,
formatters, undo, reload, and plugin edits can all change `changedtick`.

Accept and Reject stop for a stale proposal. They do not overwrite the newer
buffer state. Staged metadata remains available. |:ChatDiff| compares the saved
original snapshot with the proposal. It does not include the newer user-edited
buffer.

Version 0.2.1 has no force-accept or force-reject command.

=============================================================================
REVIEW COMMANDS                                         *chatforge-review*

PREVIEW                                                     *:ChatPreview*

:ChatPreview [N]     Open response block N in a centered float. Default: 1.

Preview does not compare text. Buffer-local keys:

  q, ESC              Close preview.
  a                   Close and accept the first staged block.
  r                   Close and reject all fresh staged blocks.

The chat output prints the exact command for each response block, such as
`:ChatPreview 2` and `:ChatDiff 2`, so the user can preview or review the right
block without guessing its number.

DIFF                                                           *:ChatDiff*

:ChatDiff [N]        Open a new diff tab for block N. Default: 1.

For a staged block, Diff compares the saved original snapshot with the proposal.
For an unstaged block, it compares the current target buffer with the response
block. Close the tab with `:tabclose`.

                                                        *:ChatReviewDiff*
:ChatReviewDiff      Diff the lowest-numbered staged block.

ACCEPT                                                       *:ChatAccept*

:ChatAccept          Accept and write the lowest-numbered staged block.

                                                         *:ChatApply*
:ChatApply [N]       Accept and write staged block N. Default: 1.

REJECT                                                       *:ChatReject*

:ChatReject          Restore original lines for every fresh staged block.
                     Stale blocks remain pending.

NAVIGATION                                               *:ChatNextChange*
                                                         *:ChatPrevChange*

:ChatPrevChange      Jump to the first line of the first staged block.
:ChatNextChange      Jump to the last proposed line of the first staged block.

=============================================================================
COMMANDS                                               *chatforge-commands*

                                                               *:Chat*
:Chat                Open ChatForge for the current source buffer. If already
                     open, switch sessions when needed and focus the input.

                                                           *:ChatSend*
:ChatSend [message]  Send text. With no text, focus the input or send its
                     current contents. A range sends a selected-line rewrite.

                                                          *:ChatEdit*
:ChatEdit <message>  Force a live staged edit in the source buffer. A range
                     rewrites only the selected lines.

                                                          *:ChatModel*
:ChatModel [model]   Set this source buffer's model. Without an argument, use
                     `vim.ui.input`.

                                                          *:ChatReset*
:ChatReset           Ignore the current request result, reject fresh staged
                     work, clear all staged metadata and this buffer's history,
                     then redraw the chat. The underlying curl job is not
                     stopped.

Commands for review are documented at |chatforge-review|.

                                                        *:ChatBackend*
:ChatBackend         Same as `:ChatBackend status`.
:ChatBackend status  Show tracked Ollama server and model-pull job states.
:ChatBackend start   Show `ollama serve`. It does not start a server.
:ChatBackend stop    Stop a plugin-managed model pull or server job. Version
                     0.2.1 does not create a server job itself.

When Ollama is unreachable, ChatForge can show `ollama serve` or ignore the
error. When a model is missing, it can run `ollama pull <model>` as a Neovim
job, show that command, or ignore the error. `:ChatBackend stop` can stop a
plugin-managed pull. It cannot stop a server started in another terminal.

CONFIGURATION                                           *chatforge-config*

All fields are optional. Version 0.2.1 defaults: >lua

  require("chatforge").setup({
    default_model = "llama3",
    ollama_url = "http://localhost:11434",
    max_tokens = 4096,
    max_output_tokens = 2048,
    context_tokens = 64000,
    temperature = 0.2,
    highlights = {
      diff = { incoming = "ChatforgeProposedChange" },
    },
    debug = false,
    system_prompt = "You are a helpful coding assistant embedded in Neovim. "
      .. "Be concise. Use fenced code blocks with language tags for all code. "
      .. "When ChatForge context is included, it is accessible user-provided content from the editor. "
      .. "Do not claim that you cannot see that content. "
      .. "When suggesting file changes, clearly state the filename.",
  })
<
`default_model` ~
Initial Ollama model for each new source-buffer session.

`ollama_url` ~
Base URL for `/api/chat` and the health check's `/api/tags` request.

`max_output_tokens` ~
Ollama `num_predict`. It takes precedence over `max_tokens`.

`max_tokens` ~
Legacy fallback for `num_predict` when `max_output_tokens` is absent. The
default `max_output_tokens` normally makes this field inactive.

`context_tokens` ~
Ollama `num_ctx`. This is separate from the 160-line automatic context cap.

`temperature` ~
Ollama sampling temperature.

`highlights.diff.incoming` ~
Highlight group for proposed lines. The built-in `ChatforgeProposedChange`
group uses an underline by default.

`debug` ~
Show `[chatforge]` dispatch, request, parser, and backend notifications.

`system_prompt` ~
System message prepended to every request. Use an empty string to omit it.

Unknown fields remain in the merged configuration but version 0.2.1 does not
use them.

=============================================================================
OPTIONAL UI PLUGINS                                 *chatforge-optional-ui*

render-markdown.nvim ~
The chat and input buffers use the Markdown filetype. An installed and enabled
render-markdown.nvim can render those buffers through its normal filetype
handling. ChatForge does not call its API or configure it.

dressing.nvim ~
ChatForge loads dressing.nvim for |:ChatModel| and backend recovery prompts
when it is available. Native `vim.ui.input` and `vim.ui.select` remain the
fallback when dressing.nvim is not installed. dressing.nvim does not change the
chat split, message pane, preview, or diff layout.

Both dependencies are optional. |:checkhealth| reports whether they are on
`runtimepath`.

HEALTH CHECK                                           *chatforge-health*

Run: >vim

  :checkhealth chatforge
<
The check reports:

- Neovim 0.10 support
- curl availability
- whether `setup()` ran, otherwise defaults are checked
- whether `stdpath("state")` exists and is writable
- Ollama `/api/tags` reachability with a two-second timeout
- default model presence in the returned model list
- render-markdown.nvim and dressing.nvim detection

The state-directory check is diagnostic. Version 0.2.1 keeps conversations in
memory and does not persist them in that directory.

TROUBLESHOOTING                               *chatforge-troubleshooting*

`Ollama unreachable` ~
Run `ollama serve` in a terminal. Check `ollama_url`, then run
`:checkhealth chatforge`. |:ChatBackend| start only shows the command.

Model not found ~
Run `ollama pull <model>`. The recovery prompt can start this pull as a Neovim
job. Stop that job with `:ChatBackend stop`.

A proposal will not Accept or Reject ~
The target buffer changed after staging. Run `:ChatDiff N`, then resolve the
buffer manually. There is no force action. See |chatforge-stale|.

`That block is an example, not a staged implementation` ~
The request was normal chat, or a non-streamed full-file response looked too
short to replace the source. Start with `fix` or `refactor`, use
`edit file <path>`, or send a visual selection.

`Implementation #N is not staged` ~
Only stageable blocks can be accepted. ChatForge stages the first eligible
block. Later blocks may remain previewable without being staged.

Context points at the wrong path ~
Run |:pwd|. Bare `@dir`, named file paths, named directory paths, and completion
use Neovim's current working directory. Bare `@file` uses the live source
buffer.

Completion is missing a new path ~
The list is cached by working directory and capped at 80 items. Type the
reference manually, change directories, or restart Neovim.

Request debugging ~
Set `debug = true`, reproduce the problem, and inspect |:messages|.

=============================================================================
KNOWN LIMITATIONS                                    *chatforge-limitations*

- Ollama is the only backend.
- Chat and model state are not persisted.
- One request can be active at a time across the plugin.
- Reset ignores an active result but does not stop its underlying curl job.
- Existing staged work blocks the next message.
- The first fenced block in an edit response becomes proposed code.
- Inferred edit requests insert small proposed blocks at the cursor.
  Whole-file model responses that match the open buffer replace the buffer and
  highlight only changed lines. Use a visual selection for precise replacement
  of a known range.
- Multi-file patches are not applied as one transaction.
- `delete file` does not delete files.
- Staging changes the live buffer. External writes can save a proposal early.
- Reject restores memory only. It does not write the restoration to disk.
- Stale proposals have no force action. Diff omits newer user edits.
- Named staging target paths cannot contain spaces.
- Named directory context is project-relative, one level deep, and capped at
  64 entries.
- Context and completion do not read ignore files such as `.gitignore`.
- Completion is capped at 80 items and cached by working directory.
- The parser needs an opening triple-backtick fence followed by a newline.
- ChatForge defines no global mappings.
